This guide targets tailwind-variants <code>{tvVersion}</code>, the version
that the examples below run. A recipe of tailwind-variants without slots
becomes a `cva` recipe, and one with slots, or that extends a recipe with
slots, becomes an `sva` recipe. Most of the config moves over with a few
mechanical changes. The two libraries can live side by side in one app,
so you can migrate one component at a time (see
[Migrating a large codebase](#migrating-a-large-codebase)).

| tailwind-variants                                                                      | class-recipe                                                                                                                                            |
| -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tv(config)`                                                                           | `cva(config)`, or `sva(config)` with slots                                                                                                              |
| `tv({ base })`, without variants                                                       | `cva({ base, variants: {} })`, since `variants` [is required](#a-recipe-needs-variants)                                                                 |
| Arrays of classes, including shared arrays spread into them                            | One string wherever the config takes classes; `cx(...)` turns an array into one                                                                         |
| An option whose classes are `null` or `false`                                          | An option whose classes are `""`                                                                                                                        |
| A compound variant `{ size: "sm", class: "..." }`, or with `className`                 | `{ variants: { size: "sm" }, className: "..." }`                                                                                                        |
| `class` or `className` prop                                                            | `className` prop, which takes one string and ignores any other value; `cx(...)` turns an array into one                                                 |
| `slots: { base: "...", title: "..." }`                                                 | `slots: ["root", "title"]` and `base: { root: "...", title: "..." }`                                                                                    |
| In a slot recipe, `base`, an option, or a compound variant's `class` given as a string | The same classes under the slot that tailwind-variants names `base`, such as `{ root: "..." }`                                                          |
| In a slot recipe, a compound variant `{ size: "sm", class: { title: "..." } }`         | `{ variants: { size: "sm" }, classNames: { title: "..." } }`                                                                                            |
| `compoundSlots`                                                                        | A compound variant that gives the same classes to each slot in `classNames`, listed after the other compound variants                                   |
| `title({ class: "..." })`                                                              | `card({ classNames: { title: "..." } })`                                                                                                                |
| `extend: button`                                                                       | `composes: [button]`, as in [Extending a recipe](#extending-a-recipe)                                                                                   |
| `VariantProps<typeof button>`                                                          | `VariantsOf<typeof button>`, from `@lynstack/class-recipe`, in which [a required variant stays required](#a-variant-without-a-default-becomes-required) |
| `tv`, `cn(...)`, and `cnMerge(...)(config)`, which merge                               | `cva`, `sva`, and `cx(...)` from `createRecipes({ join: twMerge })`                                                                                     |
| `createTV({ twMergeConfig })`, or a `tv` of your own that passes one                   | `createRecipes` with `extendTailwindMerge`, as in [Merging classes](#merging-classes)                                                                   |
| `responsiveVariants`, from earlier tailwind-variants                                   | Breakpoint classes in the options, as in [Responsive variants](#responsive-variants)                                                                    |
| `tailwind-variants/lite`, its `cn(...)()`, and `cx`, which do not merge                | `cva`, `sva`, and `cx` from `@lynstack/class-recipe`                                                                                                    |

## A variant without a default becomes required

A variant without a default must be passed, unless it is a boolean
variant, whose only options are `true`, `false`, or both: every call that
omits it is a type error. Give it a default. To add no classes when it is
omitted, as tailwind-variants does, default to an option without classes:

<CodeComparison name="tailwind-variants/required-variant" />

Give the new option a name that the variant does not use yet, such as
`none` or `unset`; it becomes a value that the props of a component
accept. In a slot recipe, its classes are `{}`. An option without classes
that the variant declares already works too, unless a compound variant
names it, since the condition would then match calls that omit the
variant.

If every caller already passes the variant, such as a component that
destructures the prop with a default, make that value the default of the
recipe instead. Keep the component's default as well if it reads the
prop for anything else, such as a `data-variant` attribute.

## Merging classes

`tv` resolves conflicting classes by default, as tailwind-merge does, and
class-recipe keeps every class by default. A recipe that relies on the
merge, such as one with `p-4` in `base` and `p-2` in an option, keeps both
classes with the default join, and the stylesheet decides which one
wins:

<CodeComparison name="tailwind-variants/merged-classes" />

The merge also drops duplicate classes, and both builds of
tailwind-variants collapse extra spaces. The default join keeps the
classes as the config writes them, which changes snapshots of class
names, but not which classes an element has.

If you used `tailwind-variants/lite`, or `twMerge: false` everywhere,
nothing was merged: import `cva`, `sva`, and `cx` from
`@lynstack/class-recipe`. You can also design your recipes so that no
class needs merging (see
[Writing conflict-free recipes](/recipe/class-recipe/conflict-free-recipes/)).

To keep the behavior of `tv`, install `tailwind-merge` and create the
functions with it once, in a module of your own, as
[Merging classes](/recipe/class-recipe/tailwind-merge/#set-it-up) shows.
The `cx` it returns merges as `cn` does. For a recipe that passed
`{ twMerge: false }` or its own `twMergeConfig` to `tv`, create another
set of functions with `createRecipes`, with the settings of both configs
if your own `tv` combines them.

If you pass a `twMergeConfig`, build the join with `extendTailwindMerge`
from the same settings, as
[Custom theme or class groups](/recipe/class-recipe/tailwind-merge/#custom-theme-or-class-groups)
shows, with two changes:

- Move the settings of class groups that the config gives at its top
  level, such as `classGroups` or `theme`, under `extend`.
- Leave out `prefix`: tailwind-variants 3 ignores it, and tailwind-merge
  applies it, which changes the classes it merges.

A call with `className` or `classNames` runs the join again, where a call
without them reads the cache (see
[What it costs](/recipe/class-recipe/tailwind-merge/#what-it-costs)).

## Slots

`slots` lists the names of the slots, and `base` gives their classes. A
slot recipe returns an object of strings, not of functions, so `title()`
becomes `title`, and the classes that `title({ class })` adds go in the
call's `classNames`. The slot that tailwind-variants names `base` can
keep that name, but another name, such as `root`, reads better next to
the `base` property.

<CodeComparison name="tailwind-variants/card" />

A slot function of tailwind-variants can also take variants of its own,
as in `title({ size: "md" })`, which override those of the call. Call the
slot recipe again with both instead: `card({ ...variants, size: "md" }).title`.
A component that receives the slots without the variants, such as one
that reads them from a context, joins its own classes with `cx`:
`cx(slots.title, className)` gives the classes that `classNames` gives.
tailwind-variants ignores `class` and `className` passed to the slot
recipe itself, rather than to a slot, so drop them.

tailwind-variants also returns a `base` slot that the config does not
declare. It holds the classes of the config's top-level `base`, unless
`slots.base` replaces them, and of each option or compound variant that
gives classes as a string; without them, its function returns
`undefined`. A slot recipe returns only the slots that `slots` lists, so
give such classes to a slot you declare, and drop a `base` that you read
from such a recipe.

A compound slot becomes a compound variant that gives the same classes to
each of its slots. tailwind-variants adds the classes of compound slots
after those of every compound variant, so list them last. A compound slot
without conditions becomes a compound variant with `variants: {}`, which
always matches, rather than classes in `base`, which come before the
variants and so lose to them when classes are merged.

## Extending a recipe

`extend: button` becomes `composes: [button]`, which takes a list of
recipes:

<CodeComparison name="tailwind-variants/icon-button" />

`composes` merges the configs as `extend` does: it joins the `base`
classes, adds the classes of an option given again after those of the
recipe extended, merges `defaultVariants` and `slots`, and concatenates
`compoundVariants`. They differ in the order of the variants:
`extend` lists the variants of the new recipe first, and `composes` lists
those of the recipes it composes first. The classes of an element are the
same, in another order, which matters only to a join that merges
conflicting classes, where the later class wins: with `composes`, the
class of the new recipe's variant. Here, `text-xs` comes after `h-8 px-3`
in both:

<CodeComparison name="tailwind-variants/extend-variant" />

A slot recipe extends the same way, with `composes`: it has the slots of
the slot recipe it composes, and gives classes to any of them. A recipe
that declares no variants of its own still writes `variants: {}`:

<CodeComparison name="tailwind-variants/extend-slots" />

A recipe can compose several recipes, in order. `compoundSlots` stay
compound variants of each recipe, as in [Slots](#slots).

## Behaviors that change

Each example below calls the recipe before and after the migration, and
shows what it returns.

### Only a boolean variant falls back to its `false` option

tailwind-variants uses the `false` option of any variant that a call
omits and that has no default. In class-recipe, a variant with other
options is required instead, so make `"false"` its default:

<CodeComparison name="tailwind-variants/false-option" />

### A recipe without classes returns `""`

tailwind-variants returns `undefined` when a call adds no classes, and so
do a slot without classes, `cn`, and `cx`:

<CodeComparison name="tailwind-variants/empty-result" />

### A compound condition names only declared variants

The types of tailwind-variants accept a compound condition on a prop
that is not a variant, which matches when a call passes that prop, as a
component that spreads its props into the recipe does. The types of
class-recipe reject it, and the recipe warns about it when it is
created, since it never matches. Declare the prop as a variant whose
options add no classes, and the condition matches as before:

<CodeComparison name="tailwind-variants/undeclared-variant" />

For a prop that is not boolean, declare an option for each value that a
condition names, and one more as its default, such as `none`, so that
calls without the prop stay valid.

### A recipe needs `variants`

A recipe without them is a type error, and throws a `TypeError` that says
so when it is created. Pass `variants: {}`.

### A recipe lists its variants, not its config

tailwind-variants also exposes the config of a recipe, such as
`button.variants` and `button.slots`. A recipe here lists only the names
of its variants in `variantKeys`, of their options in `variantOptions`,
and their defaults in `defaultVariants`, never their classes; keep the
config in an object if you read it. `variantKeys` is a readonly array, so
a function that takes it as `K[]` needs `readonly K[]`.

## Behaviors that change with untyped data

The types of tailwind-variants reject the values below, so these changes
reach only data that bypasses the types, such as the props of a
JavaScript component or the values of a form. The calls in these
examples pass such values.

### `null` counts as an omitted prop

tailwind-variants adds no classes for a variant passed as `null`, even
one with a default:

<CodeComparison name="tailwind-variants/null-variant" />

### An empty string adds no classes for the variant

tailwind-variants uses the variant's `false` option instead, even when
the variant has a default:

<CodeComparison name="tailwind-variants/empty-string" />

### A compound condition on `undefined` matches any option

A condition on `undefined` matches any option, as a variant left out of
the condition does. tailwind-variants matches it only when the prop is
`null` or `false`, or when it is omitted and the variant has no default
or a default of `false`:

<CodeComparison name="tailwind-variants/undefined-condition" />

Name the option instead: the option that a variant without a default now
defaults to, such as `none` or `false`, or `false` for a variant whose
default is `false`. For a variant with another default, the condition
matched only untyped values, so delete the compound variant.

### A compound condition matches an option by its name

A condition on `true` matches the prop `"true"`, and one on `2` matches
the prop `"2"`, as the types of class-recipe allow. Calls with `true` and
`2` match in both libraries. tailwind-variants compares the condition
with the prop as it is, so it matches only the same type, and its cache
stores `2` and `"2"` under one key, so a recipe that receives both can
return the result of one for the other:

<CodeComparison name="tailwind-variants/option-name" />

## Responsive variants

Earlier versions of tailwind-variants had `responsiveVariants`, which took an option for
each breakpoint, such as `size={{ initial: "sm", md: "lg" }}`. Neither
tailwind-variants 3 nor class-recipe has it. Put the breakpoint classes in
the options instead, or declare an option for each responsive behavior:

```ts
const grid = cva({
  base: "grid gap-4",
  variants: {
    columns: {
      one: "grid-cols-1",
      two: "grid-cols-1 md:grid-cols-2",
      three: "grid-cols-1 md:grid-cols-2 lg:grid-cols-3",
    },
  },
  defaultVariants: { columns: "one" },
});
```

A variant passed as an object, such as `{ initial: "sm" }`, names no
option, so it adds no classes.

## Configs that throw without types

TypeScript rejects the shapes of tailwind-variants below. In JavaScript,
or in a config that bypasses the types, creating the recipe throws a
`TypeError` that names the part to fix:

- **`base` or an option as an array**, such as `base: ["a", "b"]`. Join
  the classes into one string.
- **An option of `false` or `null`.** Use `""`.
- **A string in a slot recipe.** In `sva`, a `base` or an option given as
  a string, as tailwind-variants allows for its `base` slot. Give an
  object keyed by slot name.
- **A compound variant without `variants`**, such as
  `{ size: "sm", class: "X" }`. Move the condition under `variants`.
- **A compound variant with `class`.** The error asks you to rename it to
  `className` in `cva`, or `classNames` in `sva`.

## Migrating a large codebase

tailwind-variants and class-recipe can run side by side: they are
separate packages, and a component uses whichever one its recipe comes
from. Migrate one component at a time:

1. Install `@lynstack/class-recipe`. If you use the merging build of
   tailwind-variants, install `tailwind-merge` and create the functions
   with `createRecipes` (see [Merging classes](#merging-classes)).
2. Pick a component. Rewrite its recipe with the table at the top of this
   page: `cva` or `sva`, `variants` even when empty, compound variants
   with `variants` and `className` or `classNames`, slots as a list, and
   strings instead of arrays.
3. Give a default to each variant that callers may leave out, as
   [A variant without a default becomes required](#a-variant-without-a-default-becomes-required)
   shows.
4. Replace `VariantProps` with `VariantsOf`, slot functions such as
   `title()` with the strings of the slot recipe's result, and `class`
   props with `className` or `classNames`.
5. Run TypeScript. Each error points at a call that leaves out a required
   variant, or at a config shape that changed.
6. Compare the old and the new recipe with the test below, then delete
   the old one.
7. When no file imports `tailwind-variants`, uninstall it.

### Check a migrated recipe

Keep the old recipe next to the new one while you migrate, and compare
them on every selection. `variantOptions` lists the options of each
variant, so the test can call both recipes with every combination:

```ts
// button.test.ts
import { expect, test } from "vitest";

import { button } from "./button";
import { button as oldButton } from "./button.old";

type Selection = Record<string, string | boolean>;

/** Every selection of a recipe: one option of each variant. */
function selectionsOf(
  variantOptions: Readonly<Record<string, readonly string[]>>,
): Selection[] {
  return Object.entries(variantOptions).reduce<Selection[]>(
    (selections, [variant, options]) =>
      selections.flatMap((selection) =>
        options.map((option) => ({ ...selection, [variant]: propOf(option) })),
      ),
    [{}],
  );
}

/** Passes "true" and "false" as booleans, as components do. */
function propOf(option: string): string | boolean {
  if (option === "true" || option === "false") {
    return option === "true";
  }
  return option;
}

/** The classes of a class name, in a stable order. */
function classesOf(className: string | undefined): string[] {
  return (className ?? "").split(" ").filter(Boolean).sort();
}

const callButton = button as (props: Selection) => string;
const callOldButton = oldButton as (props: Selection) => string | undefined;

test.each(selectionsOf(button.variantOptions))(
  "button(%o) has the same classes as before",
  (selection) => {
    expect(classesOf(callButton(selection))).toEqual(
      classesOf(callOldButton(selection)),
    );
  },
);
```

The test compares sets of classes, so a change in their order, which
[`composes`](#extending-a-recipe) can bring, does not fail it.
tailwind-variants returns `undefined` for a call without classes, which
the test reads as no classes. For a slot recipe, compare each slot:
`card(selection).title` with `oldCard(selection).title()`. The test passes
every variant, so it does not test what a call that leaves one out
returns; add such calls when a variant had no default before.
