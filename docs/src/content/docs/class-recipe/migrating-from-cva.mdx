The concepts are the same, so most recipes move over with a few
mechanical changes:

| class-variance-authority              | class-recipe                                                                                                             |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `cva(base, config)`                   | `cva({ base, ...config })`                                                                                               |
| `cva(base)`, without variants         | `cva({ base, variants: {} })`, since `variants` [is required](#a-recipe-needs-variants)                                  |
| Arrays or objects of classes          | One string wherever the config takes classes; `cx(...)` turns an array or an object into one                             |
| An option whose classes are `null`    | An option whose classes are `""`                                                                                         |
| `{ intent: "primary", class: "..." }` | `{ variants: { intent: "primary" }, className: "..." }`                                                                  |
| `class` or `className` prop           | `className` prop                                                                                                         |
| `VariantProps<typeof button>`         | `VariantsOf<typeof button>`, in which [a required variant stays required](#a-variant-without-a-default-becomes-required) |
| `twMerge(button(props))`              | `cva` from `createRecipes({ join: twMerge })`                                                                            |
| A `cn` helper, `twMerge(clsx(...))`   | `cx` from `createRecipes({ join: twMerge })`                                                                             |
| `cn`, imported from `"cn"`            | `cx` from `createRecipes({ join: cn })`                                                                                  |
| `cx`, which is `clsx`                 | `cx`                                                                                                                     |

## Merging classes

class-variance-authority keeps every class, as class-recipe does by
default. To merge classes with tailwind-merge, as `twMerge(button(props))`
or a `cn` helper does, create the functions with it once, in a module of
your own:

```ts
// src/lib/recipe.ts
import { createRecipes } from "@lynstack/class-recipe";
import { twMerge } from "tailwind-merge";

export const { cx, cva } = createRecipes({ join: twMerge });
```

The `cx` it returns replaces a `cn` helper: it joins its inputs as `clsx`
does, then merges them. If you use the
[`cn` package](/recipe/class-recipe/tailwind-merge/#using-cn), pass `cn`
as the join instead. To keep the imports of your components, create the
functions in the module that held your helper, such as
`src/lib/utils.ts`, and export `cx` under its name:
`export const { cx: cn, cva } = createRecipes({ join: twMerge })`.

A component that wraps a recipe call in `cn`, such as
`cn(buttonVariants({ variant, size, className }))` or
`cn(buttonVariants({ variant, size }), className)`, calls the recipe alone
instead, with `className` among its props:
`buttonVariants({ variant, size, className })`. The recipe adds
`className` last and merges it with the join. A call with `className`
runs the join again, where a call without it reads the cache (see
[What it costs](/recipe/class-recipe/tailwind-merge/#what-it-costs)).

## Behaviors that change

Each example below calls the recipe before and after the migration, and
shows what it returns.

### A variant without a default becomes required

A variant without a default must be passed, unless it is a boolean
variant, whose only options are `true`, `false`, or both: every call that
omits it is a type error. Give it a default. To add no classes when it is
omitted, as class-variance-authority does, default to an option without
classes:

<CodeComparison name="class-variance-authority/required-variant" />

The new option becomes a value that the props of a component accept.
Give it a name that the variant does not use yet, such as `none` or
`unset`; in a slot recipe, its classes are `{}`. If every caller already
passes the variant, as a component does that gives the prop a default
when it destructures it, make that value the default of the recipe
instead, and the component needs no default of its own.

### A boolean variant uses its `false` option

When a call omits a boolean variant without a default, class-recipe adds
the classes of its `false` option, and a compound condition on `false`
matches. class-variance-authority adds no classes for it:

<CodeComparison name="class-variance-authority/boolean-variant" />

### `null` is not an option

class-variance-authority adds no classes for a variant passed as `null`,
even one with a default. The types of class-recipe reject `null`, and a
`null` from untyped data counts as an omitted prop. To let a component
turn a variant off, declare an option without classes:

<CodeComparison name="class-variance-authority/null-variant" />

### A compound condition on `undefined` matches any option

A condition on `undefined` matches any option, as a variant left out of
the condition does. class-variance-authority matches it only when the
prop is omitted and the variant has no default:

<CodeComparison name="class-variance-authority/undefined-condition" />

### A recipe needs `variants`

A recipe without them is a type error and throws a `TypeError` when it
is created. Pass `variants: {}`.

## Behaviors that change with untyped data

The types of class-variance-authority reject the values below, so these
changes reach only data that bypasses the types, such as the props of a
JavaScript component or the values of a form. The calls in these
examples pass such values.

### An empty string adds no classes for the variant

class-variance-authority uses the default instead:

<CodeComparison name="class-variance-authority/empty-string" />

### A compound condition matches an option by its name

A condition on `true` matches the prop `"true"`, and one on `2` matches
the prop `"2"`, as the types of class-recipe allow. class-variance-authority
compares the condition with the prop as it is, so it matches only the
same type:
