description: "Move recipes from class-variance-authority to class-recipe: the concepts are the same, and only a few behaviors change."
---

The concepts are the same, so most recipes move over with a few
mechanical changes:

| class-variance-authority              | class-recipe                                            |
| ------------------------------------- | ------------------------------------------------------- |
| `cva(base, config)`                   | `cva({ base, ...config })`                              |
| Arrays of classes                     | One string of classes for `base` and for each option    |
| `{ intent: "primary", class: "..." }` | `{ variants: { intent: "primary" }, className: "..." }` |
| `class` or `className` prop           | `className` prop                                        |
| `VariantProps<typeof button>`         | `VariantsOf<typeof button>`                             |
| `twMerge(button(props))`              | `createRecipes({ join: twMerge })`, once                |
| `cx` (`clsx`)                         | `cx`                                                    |

Two behaviors change for most recipes:

- **A variant without a default becomes required.** Every call that omits
  it is a type error. Add a default to keep it optional.
- **A boolean variant without a default uses its `false` option.**
  class-variance-authority adds no classes for it when the prop is
  omitted.

Two more change only compound variants that name an option in an unusual
way:

- **A compound condition on `undefined` matches any option,** as a
  variant left out of the condition does. class-variance-authority matches
  it only when the prop is omitted.
- **A compound condition matches an option by its name.** A condition on
  `"true"` matches the prop `true`, and one on `"1"` matches the prop `1`.
  class-variance-authority compares the condition with the prop as it is,
  so it matches only the same type.
